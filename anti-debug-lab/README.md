# 反调试靶场 · Anti-Debug Lab

> 一个纯本地的练习环境：页面上堆满了反 F12、反右键、反复制、`debugger` 循环。
> 你要在**完全被干扰**的情况下，把 4 个 FLAG 挖出来。
>
> 这是练"对抗反调试"的题，不是练"打网站"的题。

---

## 启动

不需要 Node，不需要服务器。

```powershell
# 方式一：直接双击
start C:\attack\lab2\index.html

# 方式二：起个静态服务器（推荐，Network 面板更好用）
cd C:\attack\lab2
python -m http.server 8090
# 然后访问 http://127.0.0.1:8090/
```

> ⚠️ **建议用方式二**。用 `file://` 打开时，某些浏览器的 Network 面板不会记录 fetch 请求，会影响第 3 关。

---

## 你会遇到什么

打开页面后：

- 右键 → 没反应
- `Ctrl+U`（查看源码）→ 没反应
- `F12` → 没反应
- `Ctrl+Shift+I` → 没反应
- 试图复制文字 → 选不中
- 打开 DevTools 后页面突然变模糊、标题变成警告
- 控制台被反复清空
- 设了断点也走不下去，一直在某个 `debugger` 停住

**这些全是页面自己干的。** 你的任务是绕过它们。

## 四个 FLAG

| 关 | 藏在哪 | 大致需要什么 |
|---|---|---|
| **1** | 页面源码里 | 想办法看到 HTML 源码 |
| **2** | JavaScript 运行时 | 打开控制台，执行点什么 |
| **3** | 一个网络请求 | Network 面板 |
| **4** | 禁用 JavaScript 之后 | 换个渲染条件 |

**每关一个 FLAG，格式都是 `FLAG{...}`。**

顺带一提：页面上有一个叫 `__lab_decoy` 的东西，它是假的，别当宝。

## 规则

### 允许

- ✅ 任何浏览器、任何工具（curl / wget / 编辑器 / CDP / Python）
- ✅ 改浏览器设置、装插件、加启动参数
- ✅ 直接改本地文件来"作弊"（但那就失去意义了）
- ✅ 无限次重试

### 不允许

- ❌ 修改 `index.html` 的 JS 逻辑来"让 flag 自己出现"（不算解出来）

## 卡住了看这里（三级提示）

<details>
<summary><b>第 1 关提示</b></summary>

页面拦的是**键盘快捷键**。但"看源码"不止 Ctrl+U 一条路。

想想：拦截是 JS 做的，那如果 JS 根本没运行呢？或者如果请求根本不经过浏览器？
</details>

<details>
<summary><b>第 2 关提示</b></summary>

F12 被拦了，但浏览器的 DevTools 不止一种打开方式。

而且：第一个 FLAG 的字符串在源码里是**明文**的，第二个不是——它被编码了，只在运行时才还原。

看看页面里那个 `__lab_stage2` 函数。
</details>

<details>
<summary><b>第 3 关提示</b></summary>

页面加载时会去取一个 JSON。

你在源码里能直接看到那个文件名。
</details>

<details>
<summary><b>第 4 关提示</b></summary>

所有的反调试、所有的拦截、所有的 `debugger`——**全部都是 JavaScript**。

如果 JavaScript 不跑呢？
</details>

## 通关之后，想想这些问题

1. 这四种绕过方式，哪一种**在真实网站上做不到**？为什么？
2. `debugger` 循环为什么拦不住真正想调试的人？
3. 如果这个页面是恶意的（比如钓鱼页），以上哪些手法会真的妨碍安全研究？
4. 为什么"禁用 JavaScript"这一招对所有前端防护都有效？
